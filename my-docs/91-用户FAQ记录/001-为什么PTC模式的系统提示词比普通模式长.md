# FAQ-001：为什么 PTC 模式的系统提示词比普通模式长？

- **分析时间**：2026-08-15
- **分析方法**：会话日志（`~/.dsh/sessions/` 下 zstd 压缩的 `session.jsonl.zstd`）直读 + 源码逐行核对，关键结论均附文件路径/行号
- **涉及会话**：

| 会话 | 模式 | session id | 首条 request/header 的 system 长度 |
|---|---|---|---|
| 检查官方代码是否有更新 | PTC（agent preset `code`） | `session-f62d366d-279d-4748-8bd8-dd3a7c454591` | 35,643 字符 / 5,184 词 |
| 分析代码架构并生成时序流程图文档 | 普通（agent preset `standard`） | `session-59d9d29c-be14-4f66-815c-9c555e8d859c` | 6,100 字符 / 946 词 |

## 结论（TL;DR）

PTC 模式系统提示词约 **35.6K 字符**，普通模式约 **6.1K 字符**，相差约 **5.8 倍**。多出的 ~29.7KB（占 PTC 提示词的 83.3%）**几乎全部是同一批工具 schema 的类型化转写**，不是"PTC 多了更多行为规则"。

- **普通模式（native）**：25 个工具的参数 schema 走 LLM API 的 function-calling `tools` 数组下发（模型直接产出 JSON 工具调用），**不进系统提示词**；系统提示词里只有约 6KB 纯散文指令。
- **PTC 模式（code）**：模型只能直接调用 `run_code` 一个工具（API `tools` 数组只剩 `run_code`），其余 25 个工具的 schema 被改写为 TypeScript 类型声明（`ToolArgsMap`/`ToolOutputMap`/`declare const tools`），整体嵌入系统提示词的 `tools:sdk` 段——因为模型要**写 TypeScript 程序**去调用工具，程序内部只能引用提示词里的类型，无法引用请求侧的 JSON schema。

一句话：**工具 schema 的载体从"API 请求参数"搬进了"系统提示词"，并为了可被程序引用而改写成 TS 类型**，这是 PTC 提示词变长的直接原因。

## 证据一：会话日志（数据事实）

日志格式：每个会话一个 `session.jsonl.zstd`，解压后为逐行 JSON 事件流。

### 1.1 会话模式确认

- PTC 会话：header 事件 `{"agentPreset":"standard"}`，随后 `agent-preset/selected` 事件 `{"agentPreset":"code"}`（seq 3）——即会话内切换到 PTC（code preset）。
- 普通会话：无 `agent-preset/selected` 事件，保持 `standard`。

### 1.2 `request/header` 事件：system 与 tools 字段

两个会话首条 `request/header` 事件记录（该事件含完整 `system` 与 `tools`，体现「模型可见 ⟺ 已落日志」不变量）：

| | PTC 会话 | 普通会话 |
|---|---|---|
| `system` 长度 | 35,643 字符 / 5,184 词 | 6,100 字符 / 946 词 |
| `tools` 字段（API 下发的工具 schema） | `['run_code']`（仅 1 个） | 25 个：`ask_user_question, bash, create_goal, edit, exit_plan_mode, get_goal, glob, grep, interrupt_agent, job_kill, job_list, job_output, list_agents, ralph, read, read_image, send_message, skill, subagent, subagent_fork, todo_write, update_goal, web_search, workflow, write` |

关键事实：**PTC 的 `tools` 数组里只有 `run_code`，而普通模式的 25 个工具名恰好等于 PTC 系统提示词 `ToolArgsMap` 里的 25 个成员**——同一批工具，一个在请求参数里、一个在系统提示词里。

### 1.3 系统提示词分段（PTC）

对 PTC 系统提示词按 `## Writing code for run_code` 切分：

| 段 | 长度 | 占比 |
|---|---|---|
| 基础散文（与普通模式同源，仅多一行 `run_code` 独占指令） | 5,958 字符 | 16.7% |
| `tools:sdk` 段合计 | 29,685 字符 | 83.3% |
| └ 固定用法说明（`## Writing code for run_code` … `The available tools:`） | 1,081 字符 | 3.0% |
| └ TS 类型声明（25 个工具的 `ToolArgsMap`+`ToolOutputMap`+`declare const tools`） | 28,604 字符 | 80.3% |

### 1.4 运行时工具调用形态（`tool/call` 事件分布）

- PTC 会话：29 次 `tool/call`，**全部是 `run_code`**。
- 普通会话：45 次 `tool/call`，直接分布在各工具（`bash` 21、`read` 14、`edit` 4、`skill` 3、`ask_user_question` 2、`write` 1）。

即：PTC 下模型不直接调用工具，而是把多步操作写进一个 `run_code` 程序；普通模式下每个动作一次原生工具调用。

## 证据二：源码（机制链）

1. **preset 差异只有一行**：`apps/cli/config/agent-presets/code/agent.cordis.yml` 与 `standard/agent.cordis.yml` 的 diff 除注释外仅多一个 `tool-presentation` 行（`:259-262`）：
   ```yaml
   - id: tool-presentation
     name: '@deepseek-ai/dsh-agent-tool-presentation'
     config:
       mode: code
   ```
2. **呈现声明**：`packages/core/agent-tool-presentation/src/index.ts:63-71`——`mode: code` 时调用 `ctx.tools.presentAs('code')`，且等待宿主 `codeRuntime`（TS 代码运行后端）。
3. **两个 prompt section 的注册**：`packages/core/tools/src/index.ts`
   - `tools:code-only`（`:855-863`）：`CODE_ONLY_INSTRUCTION`（`:58`）——「`run_code` is the only tool you can call directly …」一行。
   - `tools:sdk`（`:875-892`）：非 native 模式调用 `SDK_RENDERERS[runtime.language]` 渲染；TypeScript 渲染器即 `renderToolsSdk`。
4. **可见工具收缩**：`wireSchemas`（`packages/core/tools/src/index.ts:980-1001`）——native 返回全部可见 schema；`mode === 'code'` 时 `schemas.filter(schema => schema.name === RUN_CODE_NAME)`，只留 `run_code`。
5. **SDK 段生成**：`packages/core/tools/src/ts-types.ts:249-293` `renderToolsSdk`——固定 `SDK_INSTRUCTIONS`（`## Writing code for run_code` 用法契约）+ 每个工具参数 schema 经 `jsonSchemaToTs`（`:240-247`）转成 TS 类型，拼出 `interface ToolArgsMap` / `interface ToolOutputMap` / `ToolCallError` / `declare const tools`。
6. **tools 进请求**：`packages/core/agent-loop/src/agent.ts:341,462,490`——`assembly.tools`（即 `wireSchemas` 产物）写入 LLM 请求的 `tools` 数组（`...tools.length > 0 ? { tools } : {}`）；`packages/core/session/src/types.ts:209` 的 header 记录 `tools?` 字段，保证可重建。

## 为什么 PTC 必须把 schema 写进系统提示词（设计原因）

- PTC 下模型不是产出 JSON 工具调用，而是写一段 async TypeScript 函数（erasable syntax，类型剥离后运行），内部以 `await tools.name(args)` 调用工具（`ts-types.ts:252-257`、`code-mode.ts:616-621` 的 bindings 注入）。
- 程序在 worker 内运行，**只能看到 `declare const tools` 声明的类型**；请求侧 function-calling 的 JSON schema 对程序不可见。因此必须把所有可见工具的参数/输出类型全文渲染进提示词，模型才能写出类型正确的调用。
- 普通模式下模型直接产出工具调用 JSON，schema 由 API 侧 function-calling 机制携带即可，无需进入系统提示词。
- 结论：增量 ~29.7KB 是**必需的载体迁移**，不是冗余或"规则堆砌"。

## 常见误区澄清

1. **不是 PTC 附带了更多限制/规则文本**：固定新增文本仅 `tools:code-only` 一行 + `tools:sdk` 用法说明 ~1.1KB；其余 28.6KB 全是 25 个工具 schema 的类型化转写，属于"数据"而非"规则"。
2. **与模型选择无关**：普通会话首个请求用 `deepseek-v4-pro`、中途切 `deepseek-v4-flash`，system 长度始终 ~6.1K；PTC 会话用 `deepseek-v4-flash`。长度差异只由呈现模式（native vs code）决定。
3. **与权限/审批无关**：四个 preset 都不含 approval/sandbox 行（`standard/agent.cordis.yml:8-9` 注释明确留在 host composition），PTC 与普通模式的权限完全一致。
4. **PTC 更长 ≠ PTC 更"重"**：PTC 的省 token 收益在对话侧——中间工具结果留在 worker 内存，只有 curate 后的结论进上下文；提示词侧的一次性 schema 开销是换取该收益的固定成本。

## 附录：PTC 与普通模式的优劣对比与最佳场景

### 对比表

| 维度 | 普通模式（native/standard） | PTC 模式（code） |
|---|---|---|
| 模型往返 | 每步一次 LLM 往返（N 步 = N 轮） | 多步折叠进一个 `run_code` 程序（≈1 轮 + 内部子派发） |
| 上下文增长 | 每步工具结果全部进对话，逐轮累积 | 中间结果留在 worker 内存，只有 `print`/`return` 的结论进对话（`code-mode.ts:44`） |
| token 成本 | 随步骤数与中间结果量线性增长 | 固定系统提示词增量（每次请求多 ~29.7KB）+ 程序 + 结论 |
| 延迟 | N 次串行 API 调用 | 少量 API 调用 + 程序内并发子派发（只读调用可 `Promise.all` 重叠，`ts-types.ts:256`） |
| 工具调用形态 | 模型直接产出 JSON 工具调用 | 模型写 async TypeScript 程序，`await tools.name(args)` |
| 模型能力要求 | 低（会填 JSON 参数即可） | 高（必须会写正确 TS、可擦除语法、并发与错误处理） |
| 过程可观测性 | 每步结果对模型可见，可即时修正方向 | 中间过程对模型不可见，只能靠 `console.log` 自我观察 |
| 出错恢复 | 单步失败即时反馈、局部重试 | 程序整体失败整体重写（`CODE_RUN_FAILED`，`code-mode.ts:139-144`） |
| 系统提示词 | ~6.1K 字符 | ~35.6K 字符（+29.7K SDK 声明） |
| 适合的交互 | 探索式、结果驱动、强人机交互 | 批量、确定性、可预规划的多步流程 |

### 场景推理：什么场景最大发挥模式优势

**PTC 收益最大的场景**（多步 + 中间结果大 + 路径可预规划）：

1. **批量只读分析与汇总**：读 N 个文件、过滤、汇总——doc 11 的原始例子：native 是 N 轮 tool call、每轮结果都进上下文；PTC 是一个程序，中间结果留在 worker，只有 curate 后的结论进对话（`docs 11 篇:100`）。仓库规模越大、文件越多，收益越显著。
2. **大规模检索-聚合**：`grep`/`glob` 命中成百上千条时，native 下每条都进上下文挤占窗口；PTC 在程序内过滤去重，只回传命中摘要。
3. **确定性、可预规划的多步流程**：步骤与参数在动手前就能定下来（批量改名、批量校验、跨文件机械重构），程序一次写成、并发重叠执行，成功率高。
4. **长会话 / 上下文预算敏感任务**：省下的中间结果 token 留给后续轮次，对话后期 KV 更小、检索更干净。

**PTC 劣势放大的场景**（应避免）：

1. **探索式、结果驱动决策**：下一步依赖上一步的中间输出；PTC 下模型看不到中间结果、无法中途调整策略，只能预先写死整个程序，路径不确定时失败率高。
2. **强人机交互**：用户需要过程中提问、改方向、逐步确认；普通模式每步都是交互机会，PTC 程序一旦提交就是一个原子单元。
3. **短小或单步任务**：PTC 每次请求都多付 ~29.7KB 系统提示词固定开销，几步就结束的任务收益小于成本。
4. **任务逻辑复杂易错、或模型 TS 能力不足**：程序整体失败要整体重写，debug 只能靠 `console.log` 自观察，纠错成本高。

**普通模式收益最大的场景**：

1. 交互式对话、方向变更频繁的任务；
2. 逐步探索、边看边决定（读 → 判断 → 再读）的任务；
3. 少量步骤或中间结果很小的任务（无固定开销，最省）；
4. 需要每步结果可见、可中断、可修正的敏感操作（逐步审批确认）。

### 量化权衡：固定成本 vs 边际收益

普通模式 token 成本 ≈ Σ(每步中间结果) + Σ(请求)；PTC 成本 ≈ 程序 + 结论 + (系统提示词增量 ~29.7KB) × 请求数。**当「被省略的中间结果总量 × 步骤数」超过系统提示词增量时，PTC 净收益为正**；反之普通模式更优。这正是 PTC 定位为「批处理模式」而非「默认模式」的量化原因。

会话日志形态佐证：PTC 会话 15 个 step、29 次 `run_code`（多步折叠进少量往返）；普通会话 31 个 step、45 次原生工具调用（每步一次往返）。两任务不同不可直接对比，但调用形态差异与上述机制一致。
